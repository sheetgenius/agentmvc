# Build a domain-dense Conduit backend

You have one isolated workspace and one measured coding session. Build the backend for the entire product contract provided here. Read `ENVIRONMENT.md`, `MEASUREMENT.md`, `realworld_spec/`, the small shared editor in `realworld_spec/frontend/`, and `harness/README.md` before implementation. The full API, drafts, article exports, editing links, WebSocket updates, presence, conflicts, and room cap are all in scope from the start.

Imagine this backend is one part of an agent-maintained codebase with more than three million lines. The primary design goal is **usable semantic domain density**: express as much real product behavior and as many domain invariants as possible per line and source token, while keeping the context needed to find, understand, and change a rule small. Apply exemplary care to clear terseness, cohesive modules, predictable locations, and one canonical owner for each rule. Pull out all the stops to remove incidental plumbing and repetition through the assigned framework's conventions and any libraries you judge useful. For domain logic the framework or libraries do not provide, use the language's expressive features and idioms to maximize domain signal per line. Aim for the kind of domain-rich compression Rails set out to provide.

Use this stack's idioms throughout the application that actually runs in production. The assigned framework should own the main HTTP application and its conventional routing, persistence, migration, and background-work paths. A separate server that bypasses the framework does not satisfy this goal merely by living beside its scaffold. Where the framework has no suitable feature, add the smallest focused extension and explain the choice. Favor concise, explicit domain code over boilerplate, code golf, minification, opaque metaprogramming, or hiding product rules in generated or excluded files. Density counts only when another agent can locate and safely change the behavior. You may write concise project docs, including an `AGENTS.md`, to codify how future agents should find rules, use the framework, and extend the application. The editor is a fixed client of your JSON and WebSocket protocol; write backend code and project docs only.

Your directory starts with a product-free framework scaffold. You may edit its application code and add any libraries, migrations, project docs, and Docker packaging needed to satisfy the contract. The production app is one container backed by PostgreSQL. It receives only `DATABASE_URL`, `SECRET_KEY_BASE`, and `PORT`; it must prepare a fresh database and serve the API and WebSocket endpoint without another application service. The shared frontend is served by the test/demo harness, outside the production image.

`realworld_spec/`, `security/`, `harness/`, `PROMPT.md`, `ENVIRONMENT.md`, `MEASUREMENT.md`, `.scaffold/`, and `FIXTURE.json` are read-only inputs. Do not edit, replace, skip, or filter their checks. Do not read other stacks' source or spawn subagents.

The browser environment is already prepared. Start your backend on the port in `ENVIRONMENT.md`, then run `harness/check-all.sh PORT` for the full HTTP, socket, browser, and security suite. The shared browser command copies the fixed editor to writable scratch and uses its pinned Playwright image; do not install a browser or write a stack-specific browser wrapper. The harness commands call the orchestrator's narrow check service; you do not have a Docker socket. Run your stack's formatter and linter as described in `ENVIRONMENT.md`. You may repeat checks while you work. `harness/check-production.sh PORT` builds your Dockerfile, starts fresh PostgreSQL, and runs the same acceptance suite against the production image. An independent reviewer will rerun it after you finish.

Stop when the complete acceptance suite and formatter/linter are green, or report a concrete blocker or exhausted budget. In your final report, state the check results, files that own the main rules, how the running app uses this stack's framework, libraries, and language features, implementation choices, failures and fixes, and any limits you know. The reviewer measures backend application source and agent-written project docs separately from the shared editor and harness.
