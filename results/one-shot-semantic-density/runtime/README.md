# Paired runtime measurements

The six production runs used reverse order: Rails → Phoenix → Loco, then Loco → Phoenix → Rails. Every HTTP and live run started a fresh app and PostgreSQL container. Each was limited to 2 CPUs and 1 GiB. The app received `DATABASE_URL`, `SECRET_KEY_BASE`, and `PORT`. AgentMVC's leftover demo/development containers were paused for the measurement and resumed afterward; unrelated host containers continued running. Background load is sampled in the results.

HTTP used nine scenarios at 16 virtual users each, with 3 seconds of warmup and 15 seconds of measurement: anonymous and signed-in article lists, tag-filtered list, feed, article, comments, tags, favorite toggle, and article creation. `http/STACK-roundN/results.json` records request rate, p50/p95/p99 latency, SQL statements per request, image size, cold start, memory, checks, and host load. `k6-SCENARIO.json` is the native k6 summary. `raw-SCENARIO.json.zst` and `raw-warmup-SCENARIO.json.zst` are losslessly compressed per-metric point streams.

Direct WebSocket runs used 10, 100, and 500 subscribers, with no more than 100 in one article room, and 20 saves targeted at five per second. `live/STACK-roundN.json` preserves every save and delivery sample, missing/duplicate/regressed revision counts, and idle/active CPU and memory samples. The shared Lit client was not in the measured request path.

[summary.json](summary.json) indexes all six runs. Its validator checked zero failed HTTP checks, zero missing/duplicate/regressed live revisions, matching image IDs across rounds, and all 108 compressed raw HTTP streams with `zstd -t`. The underlying per-round files are the measurement record; paired values should be read with the sampled host load. The HTTP `foreign_container_cpu_percent_max` can include k6's short-lived container, so it is not a pure unrelated-background estimate. These runs compare the finished, untuned one-shot applications on one shared host, not framework performance ceilings.
