# IHP + LiquidHaskell: three scored builds and one guided diagnostic

Three fresh, isolated Codex agents built the same Conduit backend with IHP 1.6, GHC 9.10.3, LiquidHaskell 0.9.10.1.2, and Z3 4.16.0. They received the [same frozen prompt](frozen-prompt.md), read-only contract, Lit client, browser tests, and harness. All used `gpt-6-sol` at `xhigh` effort. The [candidate preflight](preflight.json) records the product-free toolchain, proof and production probes, frozen fixture hash `26fb7e622524b0d540a564134c674ea64adc9e4817633dbbee9f84bfd5ccdecc`, and isolation checks.

## What the code shows

IHP provided schema-generated records, migrations, a front controller, WebSocket support, and a PostgreSQL-backed job worker. All three agents built working apps, but each took 44–73 minutes versus 12–20 minutes for the earlier [Rails, Phoenix, and Loco baseline](../one-shot-semantic-density/README.md). IHP's 10.2–11.0k owned source tokens fall between Phoenix's 9.0k and Loco's 11.4k; Rails remains smallest at 5.5k. Each IHP result is one implementation, so neither the elapsed time nor source count isolates the language or framework from agent choices and Nix build cost.

Run 1 concentrated much of the contract in SQL strings and JSON projections, with a wrapper for a Hasql prepared-statement failure; its LiquidHaskell setup did not prove an application rule. Runs 2 and 3 compiled a refinement used for room admission. Run 3 introduced `Application/Domain.hs`, but it chiefly groups token and share-key helpers rather than pure visibility, ownership, revision, and transition rules. These observations motivate a separate expert-guided diagnostic that asks for explicit rule ownership, set-oriented lists, and proof of a meaningful numeric invariant.

## Guided diagnostic and integrity

The [expert brief](guided/expert-brief.md) adds verified, stack-specific advice to the unchanged common prompt. Its [preflight](guided/preflight-notes.md) tested suggestions against the pinned toolchain and corrected several attractive but invalid sketches: this broker's `start` has no reload loop, the schema parser rejects inline `CHECK`, migration generation lost serial defaults in a probe, and a typed `Maybe Text` parameter did not compile in a `COALESCE` quasiquote. The guided input has its own [manifest](guided/fixture-manifest.json) and hash `98dec77242bbae3403c40e952292fcdce6ac82f2dc68fe07bb588574b80793e8`. Its measurements must retain the guided label and must not be pooled with the three identical-prompt runs.

The [guided agent](guided/agent-report.md) finished in 6,841.7 seconds, used 497,113 uncached input plus output tokens and 296 commands, and produced 14,797 owned backend tokens across 1,207 lines. Its largest file, `Api/Articles.hs`, holds 2,633 owned tokens (17.8%), versus 58.8–64.1% in the earlier IHP agents' single API controllers. It uses IHP `CanRoute` actions, set-oriented list SQL, a pure policy module, an active LiquidHaskell room bound with a negative proof probe, and an IHP job worker. The added structure increased source size by 35–45% over the scored IHP runs; a smaller file share alone does not establish easier maintenance. The [scrubbed transcript](guided/transcript.md), [source inventory](guided/source-files.json), [size](guided/size.json), and [attempt counts](guided/check-attempts.json) expose the details. The agent had 26 failed release-build attempts among 40 and one failed full-check attempt among three while resolving typed generated records and the export queue.

The reviewer reran the final source: [development](guided/development.json) passed in 16.2 seconds and [fresh production](guided/production.json) passed in 29.1 seconds. A first [production reviewer attempt](guided/production-attempt1.json) stopped in the host launch wrapper after image build, before acceptance began; the preserved log has no app error. The same frozen source passed on the next attempt. The guided agent's own development and production gates also passed.

The guided app's two [production runtime rounds](guided/runtime/summary.json) reached **651.2 / 646.6 anonymous list requests/s with one SQL statement/request**, 4,538.8 / 4,634.9 article reads/s, and 2,448.8 / 2,435.6 article creates/s. Delivery p95 at 500 subscribers was 9.87 / 9.62 ms, with no missing, duplicate, or regressed revisions. All HTTP checks passed. Its image remained 4,363.4 MB because it still packaged IHP's unoptimized server in the same Nix topology; cold starts were 0.29 / 0.27 s. As with the three scored runs, the 36 compressed raw HTTP streams and direct socket samples are under `guided/runtime/`. The one-query list is faster than every unguided IHP list, but the guided run cost more code and agent time. Its separate prompt and run order limit causal claims.

Each measured agent had a fresh Codex home with memory off and no interactive approvals. Its own directory was writable and could install dependencies; the parent repository, sibling workdirs, fixed client, spec, and harness were unavailable for writes or reads as appropriate. A broker provided Docker-backed checks without a host Docker socket. Each run used a private Nix store cloned from a clean product-free base, because an earlier isolation audit found previous source in a shared store. The [aborted migration-path preflight](preflight-aborted-run/run.json) and [research-only isolation probe](preflight-isolation-run/run.json) are preserved and excluded from the three scored builds. The eight-step repository history remains intact. Nothing has been pushed or restructured.

This small app and one-agent-per-stack baseline do not decide the three-million-line question. The next useful test is an agent changing an existing implementation across rule boundaries, migrations, and multiple instances, measuring how quickly it finds the owner and how safely the system evolves.
