# Build a Conduit backend for safe evolution

Build the complete backend specified by the frozen inputs in this workspace. Read `ENVIRONMENT.md`, `MEASUREMENT.md`, `realworld_spec/`, `security/`, and `harness/README.md` before implementation. The shared editor is a fixed client of your HTTP and WebSocket protocol. Implement the full RealWorld API, including users and authentication, profiles and follows, articles and feeds, tags, favorites, and comments, plus drafts and publication, durable article exports, editing links, live updates, presence, revision conflicts, revocation, and the room cap. The contract and checks in the frozen inputs define the exact behavior.

Imagine this backend is one part of an agent-maintained application with more than three million lines of code. A future agent should be able to find the owner of a rule, change it safely, and verify the change without reading the whole application. Optimize for **usable semantic domain density**: clear product behavior and invariants per line and source token, with small, predictable context for each change. Keep code concise and readable. Do not trade away clarity for code golf, a single large module, hidden side effects, or generated code that conceals product decisions.

Give each rule one canonical owner. Express domain decisions in names and language constructs that the compiler, interpreter, and future readers can see; avoid repeating a policy in controllers, queries, jobs, and socket handlers. Make the database enforce invariants that must hold through every entrance, such as uniqueness, references, and valid state. Keep collection queries bounded in database work as data grows: paginate in the database, avoid per-row fetches, and make counts and filters agree with the returned page. Put routing, request and response handling, persistence, migrations, background work, and delivery through the assigned framework's normal application path wherever it fits. Use focused libraries where they remove incidental work; verify their actual APIs and behavior before relying on them. Explain any necessary extension of the framework. Use maintained password and token libraries; do not write cryptographic algorithms yourself.

Treat evolution as part of correctness. Separate domain decisions from transport details so a future change to permissions, lifecycle, or revision handling has a clear place to start. Use focused tests for important rules and transitions, especially rules shared by more than one entrance. Tests should exercise behavior and failure cases rather than restate the implementation. Document the rule map and local development commands in an `AGENTS.md` of roughly 40 lines or less. Keep it useful to a fresh agent: point to owners and extension paths, not a second copy of the code.

Your directory begins with a product-free framework scaffold. You may edit its application code and add libraries, migrations, tests, project docs, and Docker packaging. The production backend is one container backed by PostgreSQL. It receives only `DATABASE_URL`, `SECRET_KEY_BASE`, and `PORT`; on a fresh database it must prepare its schema and serve the API and WebSocket endpoint, including durable background work, without another application service. The shared client is served by the harness outside that image. Write backend code and project docs only.

`realworld_spec/`, `security/`, `harness/`, `PROMPT.md`, `ENVIRONMENT.md`, `MEASUREMENT.md`, `.scaffold/`, and `FIXTURE.json` are frozen, read-only inputs. Do not edit, replace, skip, or filter them or their checks. Do not read another stack's source or spawn subagents.

Use a short feedback loop while implementing. Start the development server as described in `ENVIRONMENT.md`; on that already-running server, use a focused request or small smoke check to confirm a change in seconds. A smoke result is local feedback, not acceptance. Batch coherent edits before slower compilation. Run the stack's formatter and linter. Once the app is ready, run `harness/check-all.sh PORT` for the full HTTP, WebSocket, browser, and security suite. Stop the development server before running `harness/check-production.sh PORT` against a release or otherwise production-appropriate build and a fresh PostgreSQL database. These full gates are final checks and may take longer than the smoke loop. An independent reviewer will repeat them.

Stop when both complete gates and the formatter/linter pass, or report a concrete blocker or exhausted budget. In the final report, name the files that own the main product rules, the framework and language features used by the running app, important library choices, check results, failures and fixes, and known limits. The reviewer measures backend application source and project docs separately from the fixed client and harness.
